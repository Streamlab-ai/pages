Quick Reference
Getting started
Four steps, then the system handles the rest

Every new pilot cohort starts with the same four actions from Matt. Once all four are done, WF1 through WF5 execute automatically — no further input needed until results are ready. As of July 9, 2026, participants advance to Practice phase automatically the moment they complete their pre-diagnostic, so the weekly heat map needs no manual per-participant step either.

1
Matt's Action

Make Sure the Deal Exists in Pipedrive

The automation never creates a deal. It fills an existing deal with participants. So before anything else, open Pipedrive and check that this client has a deal in the pilot pipeline.

If the deal already exists, note which stage it is sitting in and move on to step 2.

If there is no deal yet, create one:

  1. Go to Pipedrive → Deals ↗
  2. Click + Deal in the top left
  3. Give it the client or cohort name, for example WRCCPA Pilot — September 2026
  4. Link the organisation and a contact person if you have them
  5. Choose the pilot pipeline and leave it in an early stage. Any stage except Pilot Active
  6. Save

Leaving it out of Pilot Active matters. Moving the deal into that stage is what fires the automation in step 4, and it only fires on the move. A deal created directly into Pilot Active has never moved, so nothing happens.

2
Matt's Action

Build the Cohort Roster in the Rosters folder

Open the Rosters folder ↗ in the pilots@goelevateyou.com OneDrive. Right click the roster template, choose Duplicate, and rename the new copy for this cohort. Then add each participant to the PilotRoster table.

Columns must be entered in this exact order — WF1 reads each row by column position, not by header name, so a column out of place will corrupt every row behind it:

  1. PilotName
  2. CohortID
  3. FirstName
  4. LastName
  5. Email — required, must contain @
  6. Role / Title
  7. Company
  8. ChampionName — the leader who receives Monday reports
  9. ChampionEmail
  10. PilotStartDate — format YYYY-MM-DD
  11. Notes — optional

Assign a unique Cohort ID that will identify this group across all data — for example, SF-2026-07 for Sioux Falls July 2026. Never reuse an ID.

⚠️

Never change the column order. It is hardcoded.

WF1 does not read your headers. It reads each row by column number: position 1 is the pilot name, position 2 is the cohort ID, position 5 is the email, position 9 is the champion email. Those positions are written into the automation. Renaming a header is harmless. Inserting, deleting or reordering a column shifts everything to its right and breaks the import. The dangerous version is a column inserted late, near the champion columns. Email and name still line up, so every row imports and looks fine, but the champion email field now holds a person’s name and the Monday leader report quietly never arrives. If you need to record something extra, add the new column after Notes, at the very end, where nothing reads it. If you need a field the automation actually uses, that is a change to WF1, so send it to StreamLab AI rather than editing the template.

⚠️

Always duplicate the template. Never build a new spreadsheet.

WF1 reads a named table called PilotRoster that lives inside the template file. A fresh spreadsheet has no such table, so the read fails and the deal stalls with no error message.

⚠️

The file must live in the pilots@ OneDrive.

WF1 has that drive hardcoded. A roster uploaded to your own OneDrive or a team site produces a link that looks perfectly valid, resolves, and then fails the read. Any folder inside the pilots@ drive works. Rosters is the one shared with the team.

3
Matt's Action

Fill Three Fields on the Deal

Open the deal from step 1 and set all three of these before touching the stage:

  1. Roster File URL — right click your roster file, Copy link, paste it here
  2. Confirm Pilot Cohort — set to Yes
  3. Roster Import Status — must read Not Started

Each one is a separate guard inside WF1. If any is missing the workflow stops, and most of the time it stops quietly.

4
Matt's Action

Move the Deal to Pilot Active

This is the trigger. Drag the deal into Pilot Active, and only now.

⚠️

Order matters. This is the mistake to avoid.

WF1 listens for the deal moving into Pilot Active, and reads the other three fields at that instant. Set Confirm to Yes after the deal is already sitting in Pilot Active and nothing happens, because the stage never changed. If that occurs, drag the deal out to any other stage and back in.

Participants appear in Pipedrive within seconds. The deal’s Automation Notes field is written at each step, so read it to confirm the import landed.

✓
Automation Active

WF1 through WF5 run automatically from here

WF1 imports the roster and creates Pipedrive records. WF2 sends the pre-filled diagnostic link every weekday at 8AM Central to anyone marked Not Sent. WF3 runs every Friday at 10AM Central — it matches completed responses back to Pipedrive, marks them Completed, advances Current Phase to Practice automatically so no one needs to update that field by hand, and sends a reminder to anyone still unresponded 3+ days after their initial send. WF4 then sends the weekly leader heat map every Friday at 8AM Central and delivers the Monday leader report at 8AM Central. WF5 checks every Monday at 10AM Central for cohorts with both pre- and post-diagnostic data ready, then assembles the Executive Brief data package and notifies Matt/Tamien.

Cohort ID convention
The naming rule that keeps everything organized

The Cohort ID is embedded in every form URL sent to participants. It's the primary key that flows through Pipedrive, SharePoint, and all five workflows. Use a consistent format so data stays clean across multiple cohorts.

Format — [City or Company]-[YYYY]-[MM]

One ID per cohort. Assign it when you build the roster. Never reuse an ID.

Reading the data
Where to find responses and counts

Pipedrive shows individual status. SharePoint Excel files hold the actual response data and per-cohort counts.

📊

Reading diagnostic responses

  1. Open Ripple Diagnostic Responses ↗
  2. Filter the Cohort ID column to your cohort
  3. Filter the Phase column — Pre or Post
  4. Copy/paste into AI tool or export to CSV
🔢

Getting a per-cohort count

  1. Open the Participant Send Log ↗ — one row per participant, per send
  2. Filter by the Cohort ID column
  3. Row count = total participants in that cohort
  4. Note: Pipedrive does not display group totals
Data integrity
Why cohorts never get mixed up

Three layers of protection ensure that a participant who appears in two separate cohorts generates two independent, correctly labeled records — never a merge conflict.

WF1
Cohort ID baked in at import. Every participant gets their Cohort ID the moment their roster row is processed — written to their Pipedrive Person record immediately.
WF2
Prefilled URL per person. WF2 generates a unique form URL for each participant with their Email and Cohort ID embedded as hidden fields. They never type it — it arrives pre-populated.
WF3
Email + Cohort ID matching key. WF3 uses both fields together — not email alone — to match submissions back to Pipedrive records. One person in two cohorts gets two correctly labeled entries.
Pipedrive custom fields
What gets tracked on every participant

These custom Person fields are set automatically by the workflows. You can view and filter on any of them from the Contacts → People list. To see or edit the field definitions themselves, go to Settings → Company → Data fields → Person. Changing a field’s options there will break the workflows that write to it, so read rather than edit.
